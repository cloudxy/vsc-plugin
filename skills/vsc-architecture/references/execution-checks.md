# 架构维护执行检查

每次使用 vsc-architecture 时读取本文件；它规定如何核对当前任务，详细项目计划仍按需加载。按下列环节工作，在同一交付中留下必要证据，不为每项检查另建报告。

已确定的基础设施连接属于初始化配置；功能开发不反复改端口、库名、账号或权限。应用结构升级沿显式迁移验证，连接配置沿项目 `.env` 自动加载，真实文件不提交、不打包。核对普通用户从文件配置到启动的路径，不把手工加载 shell 变量作为默认操作；新增要求并入当前任务，不丢失上一轮已授权但未交付的工作。

## 1. 恢复范围与基线

1. 从当前请求和已确认会话范围确定审查、规划或实施；记录具体交付对象。继续指令继承范围，新的明确实施请求只扩到它所指的任务。
2. 查看 `git status --short`、`git rev-parse HEAD` 和相关提交，识别已有实现及他人改动。重读当前任务台账，不把旧聊天、旧版本缺陷或发布标题当现状。
3. 为需要处理的条目建立“要求→实际入口/消费者→已有证据→尚缺内容”对应。先复核已有成果，再决定补实现、补接线还是补验收；不因发现计划落后就撤销别人的代码。
4. 区分旧审计、当前复现和候选建议。复用历史证据须写明版本与适用范围；未重新运行的测试如实标为历史记录。

## 2. 形成可以执行的任务

每个可派单任务应具备下列信息；简单变更可用短段落表达，不机械填表：

| 要素 | 要回答的问题 |
| --- | --- |
| 稳定 ID 与来源 | 对应哪项要求或已复现问题？不同轮次同名编号附来源，避免串项 |
| 输入与前置 | 使用哪个固定版本、契约、样例或已核实接口？哪些条件仅在特定路线需要？ |
| 责任与具体办法 | 哪个模块拥有事实、接口和修改？如何复用现有实现？共享文件由谁编辑？ |
| 操作步骤 | 按什么顺序检查、改变、接通消费者、验证和交接？不能只写“完善／接通” |
| 正例与负例 | 合法业务应成功什么，错误范围/并发/恢复等相关情况应怎样失败？ |
| 退出证据与回退 | 实际观察什么才完成？失败回最早的哪个责任环节？缺环境时保留什么状态？ |

跨模块的关键语义不能全部留作“实施时再定”：给出推荐方案、取舍和待核输入，先用消费者样例收敛，再编码。能够凭事实解决的技术选择由执行者完成；涉及新业务方向、创作决定或新增生产用量时沿相应已有授权流程处理。

交付前从正常用户入口走读一项任务：实施者是否还需要重新发明核心设计？能否识别先后、结果和失败处理？只有目标与验收口号而没有做法的条目仍是需求，不能标为可执行工作包。

## 3. 组织计划并消除重复

- 一个主题保留一个当前入口；总览写目标、依赖和导航，工作包写步骤，专题设计写稳定行为，台账写唯一当前状态，研究/历史标明来源和时点。简单方案可保持一个文件；职责、变更频率或阅读范围已明显不同才拆分，不以固定行数为硬门。
- 新需求先查已有主题和责任模块，不继续向总览尾部堆积；也不按每条任务或每次会话新建一份“最终版”。拆分时保留原 ID、要求及证据引用，检查承接、链接和锚点。
- 跨主题共用能力指定一个责任任务，其余任务引用其结果；不能分别建一套批准、状态、供应商能力或记忆事实。
- 依赖图与正文一致，区分工程接口、线上验证和专业效果。条件依赖须标条件；一个小任务只等待实际需要的能力，不被整个未来升级批次无条件阻塞。
- 变更记录只记当时发生的事，不继续维护第二份“当前完成度”。执行前对账，执行后只在唯一台账更新范围、版本、证据与尚缺内容。

## 4. 以消费者和证据判断完成

涉及软件体验时，按[产品与体验维护](product-experience.md)回到实际界面完成验收任务，分别核对产品目标、设计行为与实现结果。只有代码检查、截图或代理走查时明确证据范围，不据此声称真人用户满意或作品专业效果获批。

按任务适用情况分别报告，不要求每项都经历所有层级：

| 层级 | 所需证据 | 不能推导的结论 |
| --- | --- | --- |
| 已有实现 | 当前入口、代码或规则定义可定位 | 不代表正式路径使用了它 |
| 工程已验证 | 真实接口/消费者及相关正负例、命令与结果 | 离线替身不代表线上账号或服务成功 |
| 线上已验证 | 明确入口/参数组合的实际请求、输出、恢复及原生用量 | CLI 单次成功不代表其他入口或全部能力已通过 |
| 专业效果已验证 | 固定媒体版本、实际观看/听审范围、具名判断及适用条件 | 解码、静帧和测试数量不代表声音、表演或整体质量 |

函数存在时检查最终消费者；配置存在时检查实际请求；关系存在时检查用户能否完成业务。代码字符串、文件数、测试数或版本发布不能代替该任务的退出证据。

测试输入必须对应同一种业务意图。例如同一任务多次恢复应保持一次提交，用户明确新抽样则应新增真实尝试；不能用前者证明后者的文件减量或效率。对工程幂等、实际用量和用户查阅负担分别核验。

没有数据库、浏览器、权限或专业媒体时标未验证，说明缺什么；不以跳过、模拟报告或未被调用的纯函数关闭整链任务。检查范围、迁移与发布纪律沿技能正文及既有指南执行，不额外复制一套 CI 规则。

## 5. 涉及子智能体时检查运行闭环

本节在涉及角色、委派、上下文或记忆的任务中应用，不要求普通维护变更先建设完整多智能体系统。

1. 核对角色的稳定身份、职责、权限、交付物与记忆策略是否有唯一来源；角色卡字段与宿主实际注入的内容分别检查，不把文件存在视为角色已加载。
2. 区分角色 ID、本次任务实例和实际执行主体；委派固定最小输入、范围及编辑所有权，不默认继承整个父会话。自报角色或 `--by` 标签不能当作真实人工授权。
3. 核对实际存储路线的记忆写入→来源/决定→按角色与范围检索→固定快照→下次任务恢复。旧存储路径可用不代表新路径已接通；空列表、显式拒绝或未实现路线如实报告。
4. 角色记忆保留事实、依据和适用范围，方法归 Skill，当前项目事实归权威产物。检索预算限制本次读取，不等于删除审计历史；到期或来源失效的摘要停止新任务消费，不能因历史仍可读便继续自动注入。
5. 检查并行实例的冲突、幂等回写与跨项目/角色隔离。审查者可以保留自己的方法经验；独立审查隔离制作方说服性结论及当前对象的旧通过判断，复查才明确带入前次问题和修复证据。
6. 以实际任务接续与相关负例验证以上能力。宿主不支持技术隔离时说明边界，不把提示词要求或新开会话冒充强制权限及独立复核质量。

## 6. 将新经验固化并核验

重复失误或有效改进先定位原有规则：已有规则未执行就补入口/检查/真实调用；规则缺失才增加最小通用办法。仅更新私有案例记录不代表技能已学习，规则写入也不代表运行能力已实现。

关键决策留在 Skill 主文件，具体办法留在可发现的参考文件，事件和作品证据留在私有记录。维护事实只保留一个编辑来源；同步现有宿主发现与打包配置，验证通过安装路径也能读到新增引用。不要将整份聊天、项目内容或一次模型经验复制成通用强制规则。

对改变行为的规则，选择有代表性的输入做行为复核，判断实际交付和副作用；不要只测试某个词出现在文件里。以下场景可按变更范围选用：

| 输入情形 | 应观察的行为 |
| --- | --- |
| “只检查并给方案”，随后“继续” | 继续审查/规划，输出具体方法，源码与生产状态没有因此改变 |
| “将这项经验写入技能”，已有维护提交规则 | 修改所指技能及必要接线，验证并按已有授权交付；不顺便实现整套计划 |
| 旧台账说未实现，当前提交已有实现 | 核对实际消费者和证据，将缺口写准确，不从头重写 |
| 有纯函数测试或 CLI 成功样本 | 只给相应层级结论，正式链/专业效果缺证据仍保留待验收 |
| 一个大方案或多个重叠主题 | 按职责安排阅读与唯一归属，保留原任务承接，状态不复制多份 |
| 角色卡写有记忆，运行入口返回空值 | 定位未接通路线，给出实施与恢复验证步骤，不报告记忆可用 |

只对有必要的复杂规则使用独立最小上下文复核；明确其执行范围，避免让复核者按测试题中的“实施”字样操作真实项目。记录场景、实际结果和限制，失败修正规则后复核受影响情形。
